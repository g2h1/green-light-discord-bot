**Phase 4 — Messages**
- Architecture decision: sending goes straight from backend to Discord's bot-token REST API (`POST /channels/:id/messages`) — no IPC to the gateway bot process needed, since outbound sends don't require a gateway connection. Revises the Phase 3 note that assumed otherwise.
- `GET /api/servers/:id/channels` — text-capable channels for the send/schedule channel picker.
- `POST /api/servers/:id/messages/send` — zod-validated body (content and/or embed required); sends immediately via `sendChannelMessage`, or if `scheduledAt` is in the future, inserts a `scheduled_messages` row instead. Supports content, embed, up to 5 link-style buttons, `@everyone`/role/user mentions (via `allowed_mentions`, so a mention only pings if explicitly enabled — no accidental mass-pings).
- Templates CRUD: `GET/POST /api/servers/:id/messages/templates`, `DELETE .../templates/:id`.
- Scheduled messages: `GET /api/servers/:id/messages/scheduled`, `DELETE .../scheduled/:id` (cancels, doesn't delete). `backend/src/lib/scheduler.ts` polls every 30s for due `pending` rows, sends them, and reschedules `daily`/`weekly`/`custom`-interval ones or marks `none` as `sent`; failures are captured with `last_error` and marked `failed` (not silently dropped).
- `getOrCreateServerRow` (`backend/src/lib/serverStore.ts`) resolves a Discord guild id to its internal `servers` row on demand, so Messages works even if a server was never listed via `/api/servers` first.
- Central `errorHandler` now also maps `ZodError` → 400 and any thrown error with a numeric `.status` (e.g. Discord API rejections like missing permissions) → its real status, instead of a generic 500.

**Post-Phase-8 addition — Strict Channel Protection**
- Deliberately reuses existing systems rather than building a parallel one, per your instruction: config lives in the existing `server_settings` table (key `strict_channels`, an array of `{ channelId, enabled, exemptRoleIds }` — same key/value pattern as `automod`/`welcome`/`log_channels`), violations are recorded in the existing `moderation_logs` table (action `ban` or `delete_message`, `metadata.strictChannelProtection: true`), and the violation embed posts to the already-configured Moderation Logs channel (from the Logs page's `log_channels.moderation_logs`) — no separate log-channel picker was added.
- **No new migration was needed or created.** Everything is built on tables that already existed (`server_settings`, `moderation_logs`).
- Bot enforcement (`bot/src/lib/strictChannels.ts`, checked first in `messageCreate.ts` — before AutoMod, so a strict-channel violation doesn't also get double-processed by AutoMod): exempts Administrator, Manage Server, and Moderate Members permission holders, plus any role explicitly added to a channel's `exemptRoleIds`. On violation: deletes the message immediately, then bans — but only if `bot's highest role > violator's highest role` and the violator isn't the guild owner (checked before attempting, not just left to fail); if the hierarchy doesn't allow a ban, the message is still deleted and the log records `banned: false` with an explicit reason, rather than silently doing nothing or pretending to succeed.
- `bot/src/lib/moderationLog.ts` is a new bot-side file mirroring `backend/src/lib/moderationLog.ts` exactly (same table, same log-channel lookup) — needed because the bot and backend are separate processes, but it's the same logging behavior, not a second system.
- Backend: `GET/PUT /api/servers/:id/settings/strict-channels` added to the existing `settings.ts` (not a new router file, since this is config, same as automod/welcome).
- Frontend: `frontend/src/pages/settings/StrictChannels.tsx`, added as a third panel in the existing Settings page — add a channel, toggle it on/off, add/remove exempt roles from a dropdown (roles fetched from the existing `/roles` endpoint), all saving immediately on change.

## Notes
- AutoMod's anti-spam/flood/duplicate-message state is tracked in-memory per bot process (a `Map`, not Supabase) — correct for a single-instance bot (as this is, per the spec — "initially for my own Discord server, not a public SaaS"), but would need moving to a shared store (Redis, or a Supabase table) if the bot process is ever horizontally scaled.
- The `requireServerAccess` guild-list cache above is the same kind of in-memory, single-process state — same caveat applies if the backend is ever scaled horizontally.
- Strict Channel Protection's ban is permanent (no auto-unban/appeal flow) — that matches what was asked for ("automatically ban the member"), but worth confirming with the user this is the intended severity before going live, since a mistaken exempt-role config could ban a real member instantly with no undo path from Discord's side (though `POST /api/servers/:id/moderation/unban` already exists and works from the dashboard).
